# Changelog

All notable changes of FElupe Studio (the web app and the Python package `felupe_studio`, released together with the same version).

## [Unreleased]

### Added

- A project of a newer version says so (#344): if a project uses what this version does not know, a command type, a tool of `mesh.generate`, a material model, a value of an enumeration (e.g. the solver `pardiso` of v0.7 in v0.6) or a property, the first message names it before the errors of the schema, e.g. *This project uses the tool `Circle` of `mesh.generate`, which FElupe Studio 0.8.0 does not know. It may have been saved with a newer version: please update FElupe Studio.* The schema version rises only with changes that are not additive, so such a project usually has the same schema version. The app, `felupe_studio.project.loads()` and so the MCP server give the same message, tested with the shared cases `tests/data/newer_version_cases.json`; the parts that are new follow from the schema, without a list of them.
- Brands, part 2 (#321, ADR 0020): a build of the app has a brand, a folder with a `brand.json` given with `BRAND_DIR`, else the default brand `app/brand/`, which is FElupe Studio itself with the values of today. A brand sets its name and short name, its links (help, documentation, tutorial, issues, source), the text of the welcome panel, an accent color, the folder of its samples (#350) and the units of a new model; the name, the short name and the links of help, issues and source are required, so a brand inherits no identity of FElupe Studio. The JSON schema `app/src/vite/brand.schema.json` checks the file, and an invalid brand fails the build. The build writes the title, the accent color and the brand as a JSON block into `index.html`, which the app reads; *Help ▸ About* of a brand says *Based on FElupe Studio &lt;version&gt;* with its license and the source of the brand. `SAMPLES_DIR` beside `BRAND_DIR` is an error. The welcome panel says where Python runs in a sentence of its own, after the text of the brand, and its link of the tutorial is *Tutorial*.
- Brands, part 3 (#321, ADR 0020): the logo, the icons and the manifest of a brand. `logo` (SVG, required) is the logo of the header, the favicon and the manifest; `icons` (PNG of 192 and 512 px, optional) are the icons of an installed app, checked for their size. The build copies them to `brand/` and writes `manifest.webmanifest` with the names, the icons and the colors of the app, and `index.html` links the favicon, the manifest and the icon for the home screen and has the theme color. The default brand has the logo of the header of today and its icons, made by `app/scripts/make_icons.py`, which makes the icons of a brand from its logo.
- Brands, part 4 (#321, ADR 0020): the storage of a brand. `storage` (required) is the prefix of the keys of `localStorage` and `sessionStorage`, of the session in IndexedDB, of the bytecode cache (`/<prefix>-pycache`, sent to the worker) and of the cache of the service worker (`sw.js?storage=<prefix>`), so two brands on one origin keep their data apart. The default brand has the prefix `felupe-studio` and the names of today, so the settings, the sessions and the caches of existing users stay.
- Brands, part 5 (#321, ADR 0020): a self-hosted Pyodide. With `"pyodide": "self-hosted"` in `brand.json`, the build copies Pyodide into `pyodide/v<version>/` of the app, the core of the pinned npm package and the packages that the worker loads (NumPy, SciPy, rich and their dependencies), downloaded once into `app/node_modules/.cache/pyodide` and checked against the SHA-256 of `pyodide-lock.json`; `npm run dev` serves them too. The app sends the URL of Pyodide to the worker, and the service worker caches the files of a self-hosted Pyodide by their version like those of the CDN. A deployment of such a brand runs without internet access; the wheel leaves the copy out. The default stays `cdn`, so FElupe Studio and every brand without the setting load Pyodide from `cdn.jsdelivr.net` as before.

### Changed

- The samples are folders that describe themselves (#350, part 1): `app/samples/NN_<id>` with the project, the mesh files, the picture and a `sample.json` with the title, the description and the topics; the prefix `NN_` gives the order and is not a part of the id, so the ids, the archives (`<id>.felupe.zip`) and `open_sample` of the MCP server stay. `app/src/core/samples.json` is gone: the build lists the samples of the folder (`app/src/vite/samples.ts`), and Python reads them with the same rules and messages (`felupe_studio.samples`, the shared cases `tests/data/sample_folder_cases.json`). **A build takes one folder of samples:** `SAMPLES_DIR=<folder>` replaces `EXTRA_SAMPLES_DIR` (#255) and `BUILT_IN_SAMPLES=false` (#279), and there is no section *More samples* any more; to keep some samples of upstream, copy their folders. A sample may leave out its `sample.json` (the title follows from the id) and its picture (a placeholder). The MCP server reads a folder of `FELUPE_STUDIO_SAMPLES` in the same layout, lists its samples and copies only the files of a project; a folder that breaks the rules stops it at the start with the message.
- The app loads the list of its samples at runtime (#350, part 2): `samples/index.json` next to the folders of the samples, which the build writes from the folder of samples and `felupe-studio serve` makes from the folder it serves. No list of samples is compiled into the app any more, so the samples are bound loosely to it, e.g. for a brand (#321). The wheel has the samples of the build (those of `SAMPLES_DIR`, or `app/samples`) instead of always `app/samples`, so `serve` of a wheel built with other samples shows them, and so does its MCP server. A folder of samples that breaks the rules stops `felupe-studio serve` at the start with the message.

## [0.7.0] - 2026-11-19

The mesh tools of FElupe, PARDISO and a cleaner base:
- **Mesh tools:** the primitives `Point`, `Line`, `Rectangle` and `Cube` and the operations expand, revolve, embed, translate, rotate, mirror, fill between and add runouts make meshes in the app without a file or a script, with expressions of the parameters (ADR 0019). The meshes a mesh is made of are construction meshes, drawn in gray and below it in the browser; the script has one line per mesh. The sample *Bushing made with mesh tools* makes the bushing of FElupe's ex05 this way.
- **PARDISO** (Intel oneMKL) as the linear solver of a job with Python on your computer, also in single precision with a PyPardiso that supports it: `pip install "felupe-studio[serve,pardiso]"`, e.g. 7 times faster than SuperLU for a cube with 27,783 degrees of freedom on 2 cores.
- **A fixed link** of `felupe-studio serve` with the environment variable `FELUPE_STUDIO_TOKEN`, e.g. for the `.mcp.json` of an agent.
- **A cleaner base:** the code generation in parts (ADR 0018), the validation in rules per command type, one request layer in Python for both runtimes, `App` and `Viewport` in hooks and modules, and limits of the complexity in CI; the scripts, the messages and the behavior are unchanged.

The schema version stays 3: projects of v0.6 open unchanged, and the mesh tools are additive (one command type `mesh.generate` with a registry of the tools). FElupe 12.1.1, Pyodide 314.0.7.

### Added

- The sample **Bushing made with mesh tools** (#314, part 3): the bushing of FElupe's ex05 with its meshes made by the mesh tools in the app instead of a script, with the same parameters. Its meshes are those of the script, and its curve is that of the sample of the script; it solves in the browser in about 5 s.
- **Fill between** and **Add runouts** of the mesh tools (#314, part 2): quads between two lines in a plane or hexahedrons between two quad meshes (two meshes in order, a select each), and the runouts of a rubber body, like FElupe's ex05: `face = fem.mesh.fill_between(bottom, top, n=8)`, `runouts = face.add_runouts(values=[0.2], axis=1, centerpoint=[0, 45], normalize=True)`. The validation reports two meshes of other cells or points and a line that needs `embed` first.
- The operations of the mesh tools (#314, part 1): **Expand**, **Revolve**, **Embed**, **Translate**, **Rotate** and **Mirror** make a mesh of another made mesh, in a menu *Operations*, e.g. `block = face.expand(n=5, z=10)`. Their dimensions follow from their input (shared rules of Python and the app), and an input that does not fit is an issue. A mesh that another tool uses is hidden by default and shown below the mesh that uses it in the browser. The golden case `cube_expanded_from_rectangle` gives the curve of the cube read from a file.
- Meshes made by the tools of FElupe (#193, ADR 0019, part 1: the model and the script): `mesh.generate` with a registry of the tools in the schema, first the primitives `Point`, `Line`, `Rectangle` and `Cube` with expressions of the parameters in their values. Every made mesh knows the dimension of its points and of its cells and its cell type from the commands (`dimensions()` in Python and in the app): only a mesh of the dimension of the model has cell sets, a lower one is a construction mesh, and the validation says so. The script has one line per mesh, e.g. `block = fem.Cube(a=[0, 0, 0], b=[1, 1, 1], n=[3, 3, 3])`, and imports meshio only where it reads files; the checks take made meshes like mesh files. The ribbon has the tools in a menu *Primitives*. The golden case `cube_made_by_tools` gives the curve of the cube read from a file.
- Made meshes in the viewport (#193, part 2): the worker makes the meshes of the tools (`generate-mesh`), once per values of their parameters. The viewport draws the meshes of the model like imported ones and the construction meshes in gray: lines, light faces in their plane and points. An error of FElupe in a tool is a note at its mesh.
- Made meshes in the browser and the guide (#193, part 3): construction meshes are marked in the browser (*Line · n = 7 · construction*), **Export mesh…** writes a made mesh of 2D or 3D cells to a file like an imported one, and the guide has the primitives.
- Benchmarks of PARDISO (#308, part 2): `benchmark(n, precision=..., solver="pardiso")` of `felupe_studio.benchmark` in CPython, and `docs/benchmarks.md` with PARDISO and SuperLU in double precision, with the linear system and with the model in single precision. On 2 cores, PARDISO solves the cube of the spike with 27,783 DOF 7 times faster than SuperLU (15 s instead of 105 s) with less memory, and a cube with u-p-J 8 times faster; with the model in single precision in 7 s.
- PARDISO of Intel oneMKL as the linear solver of a job (#308, part 1), for large 3D models in Python on your computer (`felupe-studio serve`): `solver.type` `pardiso`, *PARDISO (local Python)* in the job form, `solver=pypardiso.spsolve` in the script with `import pypardiso` only where a job uses it, also in single precision with a PyPardiso that factorizes in float32 (e.g. adtzlr/PyPardiso). The extra `felupe-studio[pardiso]` installs PyPardiso. The runtime says what it has in its `ready` message (`felupe_studio.capabilities`): in the browser, or without PyPardiso, a job with PARDISO has an issue (*PARDISO needs Python on your computer*), also in the MCP server and before a run; the model stays valid in every runtime. *Help ▸ About* of the local runtime shows the version of PyPardiso. The golden case `bar_pardiso` gives the curve of SuperLU.
- The token of `felupe-studio serve` from the environment variable `FELUPE_STUDIO_TOKEN`: it stays the same at every start, so a `.mcp.json` of VS Code or Claude Code takes it as `"Authorization": "Bearer ${FELUPE_STUDIO_TOKEN}"` without a secret in the file, and the link of the app stays the same. A token needs at least 16 letters, digits, `_` or `-`; with it, `serve --agent` prints the header of the `.mcp.json`. The guide for agents shows the `.mcp.json` in the root of the workspace for the stdio server and for the agent bridge.

### Changed

- Limits of the complexity of a function in CI (#313): ruff checks a complexity of at most 15 in Python (C901), ESLint at most 20 and 150 lines per function in the core, the worker, the viewer and the agent of the app, and warns above 30 and 250 lines in the components and hooks of the UI. The functions above the limits are split: the parser, the evaluator and the walker of the expressions in Python and in the app, `check()` of the checks, the details of the browser tree as a registry by command type, the errors of the fields of a form as a registry by the type of input, the plan of a mesh import and the sections and layers of the viewer. The MCP servers keep their tools as nested functions with a reason for the exception. The behavior is unchanged: the expressions of a corpus evaluate the same, and the browser trees of the 55 projects and command lists of the tests and the samples are identical. CONTRIBUTING.md lists the limits and why.
- `ResultsView`, `CommandForm` and `fieldSpecs()` in modules (#312, part 3): the scenes of the results (`useResultScene`), their drawing (`resultsDrawing`), the pointer (`useResultsPointer`) and the cards (`ResultsCards`); the state of a command form (`useCommandForm`), the text of its fields (`formText`), its controls as a registry by the type of input (`FormControls`) and its rows (`FormRows`); and `fieldSpecs()` with a function per kind of property. No component or function of the app has more than about 400 lines; the behavior and the tests are unchanged, and the fields of 719 drafts (all command types, the golden cases, the samples and the validation cases) are the same.
- The component `Viewport` in modules (#312, part 2): `usePicking` (a picked face, picked surfaces with their feature angle, picked nodes, the tip and the click of the viewer, now in small functions of a node, a face and a control point), `useOverlays` (the faces, markers and lines of the objects and the warnings about the selected object) and `ViewportPanels` (the toolbar and the panels of the picks, with the presets of the commands they create). `Viewport` has 277 instead of 1010 lines; the behavior and the tests are unchanged.
- The component `App` composes hooks by concern (#312, part 1): `useProject` (the name, saving, opening files, archives and samples, a new project, the session), `useResults` (the run, the shown and the live results, the player, the contour, Solve), `useSelection` (the selection, the hidden objects and the context menu of the browser), `useExports`, `useShortcuts` (the shortcuts as tables), `useAppAgent` and `useDialogs` with the component `Dialogs`, and `ResultsPane` and `Banners`. `App` has 377 instead of 1267 lines; the behavior and the tests are unchanged.
- One request layer for the Pyodide worker and `felupe-studio serve` (#311): `felupe_studio.requests` answers the 12 requests of the app (`write-file`, `inspect-mesh`, `make-mesh`, `run`, `script`, `script-view`, `check`, `result`, `result-ranges`, `export-results`, `export-mesh`, `benchmark`) for both runtimes, instead of a second implementation in the worker. The worker passes the frame of a request to `handle_frame()` and gets the JSON text and the buffers of every answer, the parts of a frame (`felupe_studio.frames`), so both runtimes get the same messages; it keeps loading Pyodide and the wheels, the bytecode cache and the transfer of the arrays (`pyodide.worker.ts`: 214 instead of 462 lines). The protocol of the app is unchanged.
- The code generation in parts (ADR 0018): `codegen()`, one function of 559 lines with a complexity of 105, is a fixed sequence of parts (`PARTS`), each a function of a `Context` that is computed once from the resolved commands, with an emitter per command type in a registry of its part. The parts are in the modules `sections`, `sets`, `items` and `jobs`, the formatting like ruff in `formatting` and `object_lines()` in `lines`; `felupe_studio.codegen` keeps its public API. No function of the code generation has a complexity above 15, and the scripts are byte-identical: the golden scripts and the scripts of all 333 command lists of the tests (#309).
- The validation in rules per command type (#310): `_reference_errors()` (261 lines, a complexity of 51) and `analysis_problems()` (28) in Python and `validateResolved()` (75) and `analysisProblems()` (48) in the app are small rules `(model, command) -> problems` in registries by command type, with the same names in `felupe_studio.rules` and `app/src/core/rules.ts` and the rules of a 2D model in `felupe_studio.analysis` and `app/src/core/analysis.ts`. The kinds and references of the app are in `app/src/core/kinds.ts`. No function of the validation has a complexity above 15, and the messages are identical: the 504 command lists that the tests validate give the same messages in Python, and the same issues with their fields in the app.
- The documentation of v0.7 (#315): the user guide has a tutorial of the mesh tools (the bushing of ex05: lines, embed, fill between, runouts, revolve) with pictures of the tools and of the section, and the limits of version 0.7; the README lists what 0.7 adds; the release checklist has the smoke tests of the mesh tools, PARDISO and the fixed token. `docs/make_screenshots.py` makes the two new pictures, and the roadmap links go to #317.

## [0.6.0] - 2026-11-19

A local Python runtime, the agent bridge, large models and expressions of parameters:
- **Python on your computer:** `felupe-studio serve` runs the same app with the Python of your computer instead of Pyodide (ADR 0014), and the package with the built app is on PyPI.
- **Agents on the open app:** with `felupe-studio serve --agent`, an agent like Claude Code works on the model that is open in a tab (ADR 0015). Its changes are steps of the history, and its mesh scripts run only after the user agrees.
- **Expressions of parameters:** the numbers of the commands may be expressions of the parameters, e.g. `0.5 * layers * height` (ADR 0013).
- **Large models:** single precision of the linear equation system of a job, or of the whole model with an estimate of its round-off (ADR 0016), and a bytecode cache that halves the FElupe step of the start in the browser (ADR 0017).
- **Touch screens:** a long press picks like Shift+click.

The schema version stays 3: projects of v0.5 open unchanged, and the new options are additive (expressions in number fields, `precision` of `model.settings` and of the solver of a job). FElupe 12.1.1, Pyodide 314.0.7.

### Added

- A model in single precision (ADR 0016): *Precision* of the *Model settings* (`model.settings.precision`: `double` or `single`) builds the regions, the fields, the stresses and the linear equation system in `float32`, in half the memory. The script has `DTYPE = np.float32`, the regions `.astype(DTYPE)` and the fields `dtype=DTYPE`. As the accuracy of single precision depends on the model, the job panel shows an estimate of the round-off of the forces relative to the reaction forces, e.g. *round-off 0.65 % of the reaction forces*. From 1 % on it warns and suggests double precision, e.g. for steel bonded to rubber (the sandwich spring: 43 %, its curve deviates by 4 %). The curves deviate from double precision by about a tenth of the estimate, or by the tolerance of the job if that is larger: within 1e-3 for the golden cases and the samples with an estimate below 1 %, except the elastic-plastic plate (2e-3 at its tolerance of 0.01, 3e-5 at 1e-6). Elastic-plastic materials keep the linear equation system in double precision (their tangent of FElupe), and the friction block does not converge in single precision. The benchmark of the spike (`spike.html`) runs the model in single precision too: in CPython, a cube with 14,739 DOF solves in 9.9 s instead of 28 s, in 188 MB instead of 317 MB (#297).
- A bytecode cache of Pyodide (ADR 0017): the worker keeps the bytecode of the imported modules (NumPy, SciPy, FElupe, meshio, tensortrax, `felupe_studio`) in IndexedDB and reads it at the next start, instead of compiling about 740 modules again. The FElupe step of the start takes about half the time from the second start of a version on: 3.9 s → 1.6–1.8 s in Chromium on a desktop. The first start fills the cache in the background; a new version starts a new cache and removes the old one. The cache is optional: without IndexedDB (e.g. in a private window) the start is as before. `spike.html` lists the parts of the FElupe step (wheels, NumPy and SciPy, FElupe, meshio) and the state of the cache (#49).
- The linear equation system of a job in single precision (ADR 0016): *Precision* of a direct solver (`solver.precision`: `double` or `single`) solves the linear system of every Newton iteration in `float32`, with the model, the residual forces and the convergence check in double precision. The curves are those of double precision (within 2e-5 for the golden cases and the samples), with up to a quarter less memory and up to two times faster for large models. The script wraps the solver, `solver=single_precision(fem.solve.SuperLUSolver())`; the job panel says *SuperLU, single precision*. The Pyodide benchmark (`spike.html`) runs in both precisions (#152).
- `felupe-studio serve --agent`, the server side of the agent bridge (ADR 0015): an MCP endpoint at `/mcp` (Streamable HTTP, the token as `Authorization: Bearer`, no browser origins) whose tools act on the model of one connected tab of the app, which answers them over the WebSocket `/agent`: the tools of the MCP server (`list_commands`, `add_command`, …, `solve` with progress, `results`) and `selection`, `select`, `show` and `picture`. It prints the command that adds it to Claude Code (#258).
- The agent bridge in the app: *Help ▸ Connect an agent* connects the tab of `felupe-studio serve --agent`, and the app answers the tools of the agent on the open model: each change is an undo step with the issues of the app, `solve` runs the app's Solve with its live results and reports the progress, `show` and `picture` give the agent the view, `select` and `selection` the selection of the user. A mesh script of the agent runs only after the user agrees (*Show the script*, *Run it*). `check` runs the checks of the mesh data in the local runtime. The status bar shows the connection with *Disconnect* (#258).
- `felupe-studio serve`, the server of a local Python runtime (ADR 0014): it serves the built app on `127.0.0.1` and runs the Python side with the CPython of the computer, with the messages of the Pyodide worker over a WebSocket (binary frames for the arrays), one Python process with a temporary folder per connection (closing it ends a running job), a token in the URL and only the hosts and the origin of the loopback interface. It needs `pip install "felupe-studio[serve]"`; the wheel has the built app (without the files of Pyodide) and serves the samples of the package (#240).
- The app of `felupe-studio serve` uses the local Python: the same requests over the WebSocket, typed arrays like from the worker, *Cancel* by a new connection (a new process). The status bar says *FElupe 12.1.0 ready, local Python 3.13 (0.5 s)*, *About* lists the runtime and its versions and reports a package of another version than the app. Opening a project with mesh scripts shows them before they run, also without parameters: they run on this computer with your rights. No service worker; the token of the link is kept for the tab, so a reload works (#240).
- Expressions of parameters in the numbers of the commands (the core, ADR 0013): a number field holds a number or an expression as a string, e.g. `"end": "0.5 * layers * height"` or `"value": "height"`, with numbers, the parameters, `pi`, `+ - * / **`, parentheses and `sqrt exp log sin cos tan abs min max`. The schema gives these fields the types `["number", "string"]`; the fields of `parameter.add`, the tag of a cell set, the ids of a point set and the decimals of the merge stay numbers. Python and the app evaluate an expression with the same parser and the same messages (shared cases), e.g. *'layer' is not a parameter in '0.5 * layer * height'*, *'cells / 3' is 1.3333333333333333, not an integer* or *'1 - cells' is -3, it must be at least 1*; the validation reports them first and checks the other rules with the values. The script shows an expression as written, e.g. `fem.math.linsteps([0, (0.5 * layers * height)], num=(2 * cells))`. The viewer, the validation and the runs of the app use the values, the browser shows the expressions; renaming a parameter renames it in the expressions. A golden case is the sandwich spring with expressions (#242).
- Expressions in the forms: a number field takes an expression of the parameters (a leading `=` is fine) and shows its value with its unit below it, e.g. *= 12 mm*, also in the rows of a ramp; a list of numbers takes expressions separated by commas, e.g. `0, 0, height`. The form checks an expression with the values of the parameters and its value against the range of the field, e.g. *'1 - cells' is -3. Must be at least 1.* In a model with parameters, these fields have a text keyboard on touch screens. The issue of a stored expression is shown at its field, also in a row. The dialog of the parameters says which objects use a parameter and warns of the problems of the expressions with the typed values, e.g. too few increments (#242).
- `felupe-studio` on PyPI: `pip install "felupe-studio[mcp]"` installs the Python package and the MCP server without a clone. A tag `vX.Y.Z` publishes it by a release workflow with trusted publishing (no token): it checks that the tag is the version, builds the sdist and the wheel, checks the wheel in a fresh environment outside of a clone, and uploads them. The wheel contains the samples and the documents of the MCP server (its resources), so `open_sample` works outside of a clone too; a clone still uses its own folders, and `FELUPE_STUDIO_SAMPLES` another one. The README on PyPI has absolute links to GitHub. CI builds and checks the wheel on every push (#275).
- A build without the built-in samples: `BUILT_IN_SAMPLES=false` (with `EXTRA_SAMPLES_DIR`, e.g. for a deployment with only private samples) leaves them out of the app and of the build output; the extra samples are then the samples, without the section *More samples*. Without any samples, the welcome panel has no samples and *File ▸ Samples…* is gone. Without the parameter, the build is unchanged (#279).
- A long press picks like Shift+click: hold the pointer still for half a second to cycle a single face or to add a node, also on a touch screen without Shift. A ring at the pointer shows it; a drag (a rotation) or a second finger cancels it. On a touch screen the hints speak of taps and long presses, e.g. *Long-press single faces* and *tap again to exclude* (#273).

### Changed

- The sample *Sandwich spring with parameters* shears by an expression of the parameters, half of the height of the soft layers (`0.5 * layers * height`, 12 mm for 3 layers), in `2 * cells` increments: with 5 layers it shears by 20 mm to the same shear strain. The guide, the README and the release checklist describe version 0.6, with new screenshots of the expressions and of an agent on the open app; `docs/make_screenshots.py --pyodide <folder>` serves Pyodide from a folder if its CDN is not reachable (#276).
- FElupe 12.1.1 (the wheel of the app, the golden tests and `felupe>=12.1.1` of the package). It imports `scipy.interpolate` and `scipy.special` only when they are used (adtzlr/felupe#1297), so `import felupe` in Pyodide takes 0.4 s instead of 1.2 s without the bytecode cache and 0.1–0.2 s instead of 0.4 s with it (Node). It also has the fixes for a model in single precision: a region keeps its precision after `field.merge()` (adtzlr/felupe#1293), and the default absolute tolerance of the Newton-Raphson method in single precision (adtzlr/felupe#1294). The curves of the golden cases are unchanged.
- The MCP server refuses a command with the name of another one (*Not added: there is already an object 'right'.*) and a rename to an existing name, like the agent bridge of the app; before, it added it and the validation reported it. Shared cases check that both give the same answers (#258).
- Values at the points: the strain and the stress tensors are moved to the points, and their principal values and the von Mises stress are evaluated there, instead of moving the invariants of the quadrature points. So the von Mises stress is never negative, e.g. next to the air of the engine mount (it was down to -0.27 MPa projected), and the principal values are those of the tensor at a point. The equivalent plastic strain is clipped at zero. The values at the cells are unchanged (#274).

### Fixed

- The sample *Elastic-plastic plate with a hole* did not solve in the browser: in Pyodide, the Newton iterations of the tenth substep of the loading did not converge (the spreading yield zone is sensitive to the round-off, which differs from CPython). Its job cuts back a substep that does not converge now, and the curve is the same within the tolerance of the job.
- A form with an error in a row, e.g. in the end value of a ramp, is not applied; it was applied before, and the validation reported the value (#242).

## [0.5.0] - 2026-11-18

Plasticity, results at the points, samples and an agent interface: the strain-based materials of FElupe 12.1 (`fem.MaterialStrain`) bring linear elasticity and von Mises plasticity with isotropic hardening, in small strain or in a framework of large deformations, with the state variables of every substep in the results (the sample *Elastic-plastic plate with a hole*). The strains and the stresses are shown at the cells or smooth at the points of the meshes, also in the exports. - FElupe 12.1.0 (the wheel of the app and the reference of the tests, `FELUPE_VERSION` of the CI; the WebGL viewer is unchanged). Its Newton-Raphson method checks the convergence relative to a reference force, the reaction forces or the forces between the items if they are larger (e.g. of a pressure or a contact on a solid body), with an absolute tolerance at the round-off errors instead of 0.001: a job with the default tolerance may take fewer iterations. The curves of the golden cases agree within 1e-8, except `block_pressure` with the default tolerance: its forces change by up to 0.7 % of the largest force, and both versions deviate by less than 1 % of it from the converged curve.

The discretization is the same: converged results agree within 1e-9. The system has about a third fewer unknowns. At the default tolerance a job may take a few more Newton iterations but ends closer to the converged result (see `docs/benchmarks.md`). Other cells (tetrahedrons and triangles with the MINI element, quadratic cells) keep the mixed fields. The generated script has the helpers `mixed_field()` and `nearly_incompressible()` (only with a `u-p-J` section), so `mixed_field`, `nearly_incompressible` and the other names of the helpers are reserved (#226).

- More material models of tensortrax (`fem.Hyperelastic`): Yeoh (C10, C20, C30), third-order deformation (C10, C01, C11, C20, C30), Ogden (one to three terms μᵢ, αᵢ as lists), Arruda-Boyce (C1, limit) and extended tube (Gc, delta, Ge, beta), each with an optional bulk modulus. They are definitions of the material registry of the schema with labels, units, bounds and the defaults of the FElupe examples; Ogden needs as many exponents as moduli (`x-same-length`, checked in the form and the validation) and no exponent of zero. The *Materials* tab groups the models in menus (*Neo-Hooke ▾*, *Polynomial ▾*, *Micromechanical ▾*, by `x-group`), so it stays one row. Golden cases `cube_<model>` pull a cube to a stretch of 2 and compare the curve with `fem.ViewMaterialIncompressible` (#136).
- Scale of an imported mesh: `mesh.import` has a `scale` (default 1) that multiplies the coordinates after reading, before the cell sets, e.g. 1000 for a mesh in m of a model in mm. The import dialog shows the size of the mesh and suggests the scale for a mesh that is very small or very large for the units of the model (smaller than 1 mm or larger than 10 m; without units, smaller than 0.01 or larger than 10000). The viewer, the point sets and the points, the checks of the interfaces and the script use the scaled coordinates (#135).
- The volumetric part of the u-p-J formulation: the section property *Volumetric part* (`volumetric`, only with u-p-J) chooses the strain energy U(J) of `fem.NearlyIncompressible`, *volume-ratio* K/2 (J − 1)² (default), *stretch* 9K/2 (J^⅓ − 1)² or *log* K/2 ln(J)², with the formulas in the options. The script passes it only if it is not the default; the browser shows it at the section. Tests compare all three with FElupe; a golden case (`bar_volumetric_log`) pulls a bar with a small bulk modulus and *log*. The bulk modulus of a section shows the unit of the model (#134).
- Settings of the Newton-Raphson method and of the cutback of a job: *Max. iterations* (`maxiter`) next to the tolerance, and with a cutback its *Factor*, *Max. cutbacks* and *Growth* (`cutback: {factor, max_cutbacks, growth}`, the parameters of `fem.CutbackPlugin`), each optional with the default of FElupe. The script passes only the given ones; the job panel shows *Newton iteration 3 of 16*. Optional groups of fields in the forms show their hint. A golden case (`bar_cutback`) needs a cutback by a smaller factor (#133).
- Units of the model: the new command `model.settings` (at most one, *Model settings* in the *Mesh* tab) says what the numbers mean, the units of lengths (mm, m) and forces (N, kN); stresses follow (MPa, GPa, Pa, kPa). FElupe has no units, nothing is converted. The forms show the units at their labels (from `x-quantity` of the schema), also at the rows of the ramps; the browser at the values, the results at the scalar bar, the tooltips, the control points and the curve, and the CSV of curves and control points in the header (e.g. `u_x [mm]`); the script gets a comment. Rotations are always in rad. The samples *Rubber mount in shear* and *Rubber block with a rigid plate* are in mm and N (#132).
- Script view: the ribbon tab **Script** shows the FElupe script of the model instead of the viewport, as it is exported and updated after every change, with highlighted Python and line numbers. The lines of the selected object are highlighted, a click on a line selects its object; *Copy* and *Download*. `felupe_studio.codegen.object_lines()` finds the lines of the objects (#130).
- Keyboard shortcuts: Ctrl+S save, Ctrl+O open, Ctrl+Enter solve, Delete and F2 for the selected object, Esc clears the selection; F, 1–4 and N in the views; ←, →, Home and End step through the substeps; `?` opens the overview. One list (`core/shortcuts.ts`) feeds the handlers, the overview, the menus (with `aria-keyshortcuts`) and the tooltips. Not while typing, except saving and solving (#129).
- A welcome panel for an empty model: *Import mesh*, *Open project*, the samples as cards with a picture, and links to the user guide and the tutorial. The pictures (`thumbnail.svg`) are made by `make_samples.py` from the models, in the colors and the default view of the viewport; the Samples dialog shows them too (#127).
- **File** and **Help** menus in the header: File has new, open, samples, save and the exports; Help links the user guide, the command reference and a new issue, lists the keyboard shortcuts and shows *About* (versions of the app, FElupe, Python, Pyodide, NumPy, SciPy, meshio and tensortrax, the load time, the license, the Pyodide benchmark). The menus work with the keyboard (#126).

### Changed

The layout below 800 px no longer stacks the panels below the viewport (#131).

Multi-point constraints: control points, rigid connections of point sets with rotation points, point loads, and steps that ramp several items with their own values. Projects of schema version 1 (v0.1) are migrated when they are opened; projects saved with v0.2 have schema version 2. With a user guide and a command reference.

### Added

- Documentation: a [user guide](docs/guide.md) with a tutorial, and a [command reference](docs/reference.md) generated from the schema (`python docs/make_reference.py`); the schema describes all properties, which the forms show as hints (#33).
- Sample *Rubber block with a rigid plate*: a multi-point constraint with a rotation point, moved and tilted in one step (#102).
- Results of control points: displacement and force (rotation and moment of a rotation point) on hover, in a card per substep and as CSV of all substeps (#101).
- Point loads (`load.add`, `fem.PointLoad`) on point sets and control points, ramped by the steps as a factor of the force; force-controlled curves; arrows in the viewport (#100).
- Multi-point constraints in the viewport: lines from the center to the connected points, also displaced in the results, and a warning for points that a boundary prescribes as well (#99).
- Curves of rotation points show the moment over the rotation (*Moment–rotation*); the properties say when values are rotations (#98).
- Multi-point constraints (`mpc.add`, `fem.MultiPointConstraint`): the points of a point set follow a control point, optionally with a rotation point; items of the steps (#97).
- **Control point at center** of the selected point set, of a picked face or of picked nodes (#96).
- Control points in the viewport: drawn as markers (also displaced in the results), selected by a click, listed under **Points** in the browser (#95).
- Control points (`point.add`): points that are not nodes of the meshes, merged as a mesh of vertices and referenced like a point set, e.g. by a boundary (#94, ADR 0006).
- Picking nodes: with **Nodes** shown, a click picks a node, Shift+click more; create a point set of them, add them to the selected one or copy their coordinates (#93).
- Point sets by nodes: the coordinates of points, one per line, stored by coordinates instead of ids of the merged mesh; the viewport warns about coordinates without a node (#92).
- **Nodes** in the view toolbar shows the nodes of the visible meshes, also in the results (#91).
- A tolerance of the Newton-Raphson method per job (`tol`), e.g. 0.05 to loosen it (#106).
- Boundaries and load cases in the viewport: strokes of the fixed components and arrows of the moved boundaries, also of the load cases like `fem.dof` (#82).
- Results: hovering shows the value under the pointer, of a cell (strains, stresses) or of a node (displacements), with its cell or node (#85).
- Samples (header and empty model): four finished models with their mesh files, opened like a project file (#32).
- The properties of the selected object are shown in a panel on the right of the viewport, which opens on selection and can be closed; the browser has the left sidebar for itself (#83).

## [0.1.0] - 2026-11-10

The first release: a model of hyperelastic solids, from mesh files to results, in the browser.

### Model

- Import mesh files (VTU, Gmsh and the other formats of meshio) with one or more types of solid cells; cell sets from cell tags or from whole mesh files; merge points of meshes with a tolerance.
- Materials of the material registry: Neo-Hooke, Neo-Hooke (compressible), Mooney-Rivlin and linear-elastic (large strain).
- Sections with the displacement formulation (`u`) or the mixed formulation (`u-p-J`, MINI element for linear tetrahedrons) for every supported cell type.
- Point sets by a plane or by point ids, also by clicking a face in the viewport; boundaries, load cases of `fem.dof` (uniaxial, biaxial, planar, shear) and ramps of several boundaries.
- Steps and jobs, with a force-displacement curve of a boundary and an optional cutback.

### App

- Desktop layout bound to a command list with undo and redo: ribbon, browser, generated properties forms, command line and history.
- Project files (`.felupe.json`): a text-diffable command list.
- WebGL2 viewport with the viewer of FElupe: cells colored by mesh, cell set or section, visibility, point sets as markers, view toolbar and axis triad.
- Solve in a Pyodide worker with live progress (substeps, Newton iterations), cancel and the Python traceback of a failed run.
- Results: deformed shape with contours of the displacement, the principal logarithmic strains and Cauchy stresses and the von Mises stress per substep; the force-displacement curve with a table and CSV.
- Exports: the FElupe script of the model, the results as XDMF (all substeps) or VTU (a substep), and a PNG of the view.
- A service worker caches Pyodide and the wheels, so later visits start faster; a notice reports a newer deployment of the app.

### Python package

- `felupe_studio.codegen()`: the command list as a readable FElupe script, checked by golden tests against reference curves.
- JSON schema of the command list (schema version 1) as the single source of the app and of the package.
